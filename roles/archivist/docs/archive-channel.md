## 2. Схема наполнения (утверждена 04.11.2026)

Один файл — один пост. Тип вложения выбирается по файлу, чтобы материал было
видно в ленте и на телефоне, и на компьютере:

| Что | Как | Почему |
| --- | --- | --- |
| фото (`.jpg .jpeg .png .bmp .tif .tiff .heic .heif .webp`) | **WEBP 1920×1440 q90 → `image`** | MAX почти не пережимает WEBP: 39,6 дБ и ~280 КБ вместо 37,3 дБ и 61 КБ у JPEG/PNG |
| готовый WEBP ≤ 1920 (например, скачанный из MAX) | **как есть → `image`** | без лишнего поколения сжатия: перекодировать уже сжатый WEBP только портит |
| видео ≤ 250 МБ | **`video`** | кадр-превью и play в ленте; MAX пережимает до 720p |
| видео > 250 МБ | **`file`** (оригинал) | в лимит `video` не влезает; на десктопе значок |
| документы и прочее | **`file`** (оригинал) | байт-в-байт |

Источники: `E:\наши изображения\мои`, `E:\наши изображения\камера` и
`E:\наши изображения\с телефонов и ноутбука` (последняя — вложения, присланные
участниками в сам канал; см. ниже).

**Битые файлы.** 74 файла с расширением фото (`.jpg`/`.JPG`) не открывались:
внутри не JPEG, а мусор от сбоя диска (случайные байты, обрывки кода). По
решению владельца (04.11.2026) они **удалены с диска** (`local/purge-broken.txt`)
и из канала (`local/broken-posts-del.txt`); в плане помечены `skip`, счётчики
заголовков пересчитаны. Список был: `local/broken-images.txt`.

Порядок ленты — хронология 2006 → 2026:

```
**2006** — 3 папки · 81 файл · 196,2 МБ            заголовок года
**2006 · димкины** — 76 файлов · 110,1 МБ          заголовок папки
  [картинка IMGP0374.JPG]  подпись «2006 · димкины» по одному посту на файл
  ...
```

Правила:

- год папки: из имени → иначе медиана EXIF-дат фото → иначе даты файлов;
- внутри года папки идут по дате события (из имени, иначе по самой ранней
  фотографии);
- файлы в корне `мои` → группа «Разное» в своём году;
- `камера` → группа «камера» в своём году;
- служебный мусор (`Thumbs.db`, `*.db`, `*.cfg`, `*.info`) пропускается;
- в конце ленты — годовые каталоги (`**2014** — 17 папок …` + перечень папок),
  последним постом — «ОГЛАВЛЕНИЕ», он закрепляется через `PUT /chats/{id}/pin`.

План на 05.11.2026: **5 801 пост**, 5 615 файловых записей (69 — удалённые
битые, пропускаются; реально 5 546 файлов, 60,4 ГБ): image 5 324, video 253,
file 38 (два видео больше 4 ГБ режутся на части, см. раздел 6).

## 4. Поведение типов загрузки (замерено 04.11.2026)

| Тип | Что происходит | Замер |
| --- | --- | --- |
| `image` из JPEG/PNG/TIFF | режет до 1920 по длинной стороне и сильно пережимает | 3072×2304 / 2,8 МБ → 1920×1440 / **61,6 КБ**, PSNR 37,3 дБ |
| `image` из WEBP | почти не трогает: тот же WEBP, ~5× больше данных | WEBP q90 1920×1440 / 300 КБ → **282 КБ**, PSNR **39,6 дБ** |
| `video` | перекодирует, отдаёт `thumbnail` и `mp4_720`/`mp4_480` | MP4 1280×720 → 756 КБ; MOV 640×480 → 68 %; **AVI 640×480 → 16 %** |
| `file` | сохраняет **байт-в-байт** | zip 196 Б и txt 64 Б вернулись с теми же sha256 |

Вывод по фото: MAX всё равно урезает до 1920 по длинной стороне, но WEBP на
входе сохраняет в 5 раз больше данных и +2,3 дБ. Поэтому фото перед отправкой
конвертируются в WEBP 1920×1440 q90 (кэш `local/webp/`).

`video` принимает и **AVI**, хотя в документации его нет, и даёт кадр-превью.
Видео >250 МБ идёт как `file` — оригинал важнее превью.

Лимиты: `image` 50 МБ и ≤ 7680×7680; `video` 250 МБ; `audio` 256 МБ и ≤ 60 мин;
`file` **4 ГБ, 1 файл на сообщение**.

Проверено дополнительно:

- кириллица сохраняется и в имени файла в MAX, и в путях внутри zip
  (`Кабардинка 2007 (часть 1 из 2).zip` вернулся с тем же именем);
- у вложения `file` есть `filename`, `size`, `fileId` и прямая ссылка
  `https://fd.oneme.ru/getfile?...` (скачивается без авторизации, байты совпали);
- resumable-загрузка не работает: POST тела с `Content-Type:
  application/octet-stream` (с `Content-Range` и без) → `406 Not Acceptable`;
  рабочий путь — multipart целиком;
- текст поста без `"format": "markdown"` сохраняет `**` литерально — формат
  указывать обязательно;
- `notify: false` в канале отклоняется: `errors.send-message.channel-notify`;
- скорость заливки на 143,7 МБ: 64 с ≈ 2,25 МиБ/с и 575 с ≈ 0,25 МиБ/с
  (сеть/троттлинг). Ориентир: 45–62 ГБ — от 8 часов до нескольких суток.

## 5. Инструменты

| Файл | Назначение |
| --- | --- |
| `roles/archivist/tools/archive_plan.py` | обход папок, определение годов, сборка плана постов в `local/archive-plan.json` + отчёт `local/archive-plan.txt` |
| `roles/archivist/tools/archive_upload.py` | исполнение плана: конвертация фото в WEBP, загрузка, `POST /messages`, GET-контроль по типу вложения, журнал, докачка, повтор при `attachment.not.ready` |
| `roles/archivist/tools/patch_plan_missing.py` | пересчёт заголовков года/папок/каталогов/оглавления по фактически существующим файлам (не меняя индексы журнала) |
| `roles/archivist/tools/dump_channel.py` | дамп последних сообщений канала в `local/channel-dump.json` |
| `roles/archivist/tools/collect_devices.py` | скачивание «входящих» вложений на диск с раскладкой по годам, манифест `local/devices-manifest.json` |
| `roles/archivist/tools/add_devices_to_plan.py` | встройка папки «с телефонов и ноутбука» в план по годам |
| `roles/archivist/tools/inbox_delete.py` | проверка и удаление «входящих» из канала (всё новее объявления, включая его) |

Запуск:

```bash
python roles/archivist/tools/archive_plan.py                 # пересобрать план
python roles/archivist/tools/archive_upload.py --dry-run --year 2006
python roles/archivist/tools/archive_upload.py --year 2006   # залить один год
python roles/archivist/tools/archive_upload.py               # последний прогон: каталоги + закреп
```

Журнал `local/archive-journal.jsonl` — по строке на пост (`i`, `kind`, `mid`,
`path`, `verify`). Повторный запуск пропускает всё со `status: done`. Ошибки
пишутся как `failed` и остаются в очереди. Отчёт прогона —
`local/archive-run.txt`.

Режим `--year YYYY` берёт только этот год (заголовки, папки, файлы), а годовые
каталоги и закреп оставляет на финальный общий прогон — иначе каталог 2006
оказался бы в середине ленты.

## 6. Два видео больше 4 ГБ: решение — резать на части

Не влезают в лимит `file` (4 ГБ):

- `E:\наши изображения\мои\2 часть Воспоминания о школе  Выпускной 2024_HD.mp4` — 8,2 ГБ;
- `E:\наши изображения\мои\Выпускной 21 школа Сальск 2024\1 часть Воспоминания о школе  Выпускной 2024_HD.mp4` — 8,4 ГБ.

Решение владельца (03.11.2026): **резать на части по 1,9 ГБ**, байты сохраняются.
Загрузчик делает это сам (`kind: file_split`):

- части кэшируются в `local/split/<имя>.part01…` (манифест
  `local/split-manifest.json`), повторный запуск не режет заново;
- каждая часть — отдельный пост с подписью «ГГГГ · Папка · часть N из M»;
- после частей — пост с инструкцией склейки (`copy /b` для Windows,
  `cat` для Linux/macOS) и sha256 исходного файла;
- проверено на тестовом файле: 4 части, sha256 исходника = sha256 склейки.

## 9. Входящие из канала: сбор и очистка

Участники кидают фото с телефонов и ноутбуков прямо в канал, под пост-объявление
(«предлагаю сюда переместить с других устройств…», «фото от Ани»). Порядок
обработки:

1. **Дамп.** `python roles/archivist/tools/dump_channel.py` → `local/channel-dump.json`
   (последние сообщения: mid, отправитель, текст, вложения). Пагинация — по
   времени (`to=<timestamp_ms>`), `from=<mid>` не работает.
2. **Сбор.** `python roles/archivist/tools/collect_devices.py` — скачивает вложения в
   `E:\наши изображения\с телефонов и ноутбука\<год>`.
   Год: дата в имени файла (`20210705_185716.jpg`) → EXIF → дата сообщения →
   **2026**, если определить нельзя. Дубли по sha256 пропускаются.
   Манифест: `local/devices-manifest.json` (путь, sha256, mid, год, размер).

   Если файлы пришли альбомами без имён (MAX отдаёт только `url`), год берётся
   из **подписи-заголовка**: подпись относится к группе, идущей **после** неё
   («уфа 2025» → следующие фото 2025 года); группа без подписи — 2026.
   Такой сбор делает `roles/archivist/tools/inbox_batch_download.py` (промежуточная папка
   `local/inbox2-tmp`, манифест `local/inbox2-manifest.json`).

   Если файлы присланы как документы (`type=file`) и у них есть имена, год
   берётся из имени (`20260503_163926.jpg`, `IMG_20250928_120825_240.jpg`), затем
   из EXIF (DateTimeOriginal), затем из подписи, иначе 2026. У каждой партии
   своя нумерация (`--batch inbox3` у общих инструментов): свои
   `inbox3-manifest.json`, `inbox3-tmp`, `inbox3-applied.txt`. HEIC/HEIF требуют
   `pillow-heif` (`pip install pillow-heif`), иначе Pillow их не откроет.
3. **Проверка дублей — три слоя** (`roles/archivist/tools/inbox_batch_dedupe.py`, затем
   `roles/archivist/tools/inbox_batch_verify.py`):
   - sha256 внутри пачки, против папки назначения и против архива
     (`мои`, `камера`) — с предфильтром по размеру;
   - dHash 8×8 внутри пачки, против папки и против архива (кэш отпечатков
     архива `local/archive-dhash.json`) — ловит перекодированные копии;
   - MAD по серому 128×128 для каждой пары-кандидата: **< 3 — копия**,
     3–8 — на ручной просмотр, **> 8 — разные кадры** (серия/бёрст).
   Порог dHash 6 даёт ложные срабатывания на соседних кадрах, поэтому
   финальное решение принимает MAD, а не dHash.
   Точные совпадения по sha256 тоже попадают в отчёт парами `d=0 … ~ путь`,
   поэтому обрабатываются тем же правилом, что и похожие.
4. **Раскладка.** `roles/archivist/tools/inbox_batch_apply.py --batch inboxN`: копии не
   переносятся; из пары копий остаётся файл большего размера (при равенстве —
   более ранний по photo_id); совпадение с архивом или с уже собранной папкой —
   пропуск, потому что в архиве лежит исходник большего разрешения. Пропуски
   тоже пишутся в `devices-manifest.json` (с `skip: true`) — это нужно для
   проверки при удалении из канала. Протокол: `local/inboxN-applied.txt`.
   Если оригинал пришёл позже, чем его WEBP-копия уже лежит в папке, оригинал
   заменяет копию (путь в плане обновляется на месте, индекс не сдвигается).
5. **Встройка в план.** `python roles/archivist/tools/inbox_batch_plan.py` (только новые файлы,
   повторный запуск безопасен), затем `python roles/archivist/tools/patch_plan_missing.py`.
   Файлы входят в свой год отдельной папкой «с телефонов и ноутбука»; годы,
   которых в плане не было (2017, 2019, 2020), получают новый блок года и
   годовой каталог. Вставка идёт после последнего залитого индекса, поэтому
   журнал не сдвигается.
6. **Заливка.** Обычным `python roles/archivist/tools/archive_upload.py --year ГГГГ`.
   **Каждое фото — отдельный пост**: альбомы не собираются, 1 файл = 1
   сообщение, поэтому все кадры видны в ленте и находятся поиском по подписи.
7. **Очистка канала.** `python roles/archivist/tools/inbox_delete.py` — только проверка;
   `python roles/archivist/tools/inbox_delete.py --yes` — удаление. Граница «входящих» —
   **первый сверху пост архива** («2011 · …», «Сканированные фото»): всё выше
   него удаляется, включая текстовые объявления. Удаление идёт **только если
   каждое вложение уже есть в манифесте** (иначе останавливается). Протокол:
   `local/inbox-deleted.txt`, копия удалённых сообщений:
   `local/inbox-deleted.json`.

Важно: папка `E:\наши изображения\с телефонов и ноутбука` **не входит** в корни
планировщика (`мои`, `камера`). При полной пересборке плана через
`archive_plan.py` её нужно встраивать заново (`inbox_batch_plan.py` или
`add_devices_to_plan.py`), иначе она выпадет из плана.

## 11. Что не публикуется

Запрет на публикацию задаётся в `roles/archivist/tools/archive_plan.py`:

```python
EXCLUDE_DIRS = [r"E:\наши изображения\мои\мульт"]
EXCLUDE_NAMES = ["свидетельство о рождении риты.pdf"]
```

- `EXCLUDE_DIRS` — папки целиком (с подпапками), сравнение по префиксу пути;
- `EXCLUDE_NAMES` — имена файлов (без пути, регистр не важен).

Действует в трёх местах: планировщик не берёт такие файлы в новый план,
`patch_plan_missing.py` ставит им `skip: true` и `excluded: true` (заголовки
пустых папок тоже пропускаются), а `archive_upload.py` пропускает всё с
`skip` — и файлы, и заголовки. В годовых каталогах исключённые папки не
