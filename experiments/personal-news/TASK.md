# ЭКСПЕРИМЕНТ «личный новостной бот»

Эксперимент живёт в основном рабочем клоне `E:\github\MAX` отдельной папкой
`experiments/personal-news/` (решение 06.11.2026: отдельный клон не нужен, пока
эксперимент не пересекается с постовыми сессиями по файлам). Рантайм-состояние —
`local/pnews_*`, токен — ключ `newsbot` в `local/tokens.json`.

РЕШЕНИЕ 06.11.2026: эксперимент ведётся на существующем боте
`@se14808890_bot` (AI Now) по фазовой стратегии (раздел «Фазы»).

## Гипотеза

Пользователь, не разбирающийся в ботах и API, может получить персональный
новостной дайджест за **2 действия**: нажать «Старт» в диалоге с ботом →
написать бриф по фиксированной форме.

## Фазы (утверждены 06.11.2026)

1. **Фаза 1 — работоспособность на @se14808890_bot.** Ручные проверки
   Ч1–Ч5 (этап 2), ядро обработки брифа и дайджеста. Токен общий
   с продовыми каналами — код эксперимента оперирует ТОЛЬКО личкой
   (см. «Гигиена кода»).
2. **Фаза 2 — бета на аудитории ainow, ≤10 участников.** Анонс-пост
   приглашением подписчикам, публикация в канале
   `https://max.ru/channel_ainow` —
   ТОЛЬКО через постовый цикл основной методики (черновик → чек-лист 5а →
   утверждение в рабочем чате → публикация) и не более одного поста в сутки.
   Подписчик: Старт → бриф → личный дайджест в диалоге. Реестр с жёстким
   капом 10 записей: переполнение — бот отвечает «бета заполнена».
3. **Фаза 3 — рост до 50.** Параллельная доработка; при приближении к 50
   участникам — регистрация второго бота заранее (модерация занимает
   время), чтобы к миграции он уже был жив.
4. **Фаза 4 — миграция при >50.** Личные функции (ассистент, контент,
   постовый цикл) переезжают на нового бота: он назначается администратором
   каналов ainow/administrator/na100, в `local/tokens.json` меняется токен
   записи, скрипты основной методики не меняются. `@se14808890_bot`
   остаётся чисто новостным: его событийный поток и реестр участников
   больше никем не делятся.

Технический порог 50 не реляционный (один токен тянет сотни личных
дайджестов в день: лимит 2 сообщ/сек на чат, poll + несколько десятков
POST — ничто рядом с 30 rps); порог — продуктовая развилка сегрегации
функций.

## Сценарий (MVP — только личка, без каналов)

1. Пользователь находит бота в поиске MAX и нажимает «Старт».
2. Пишет бриф по фиксированной форме:

   ```
   темы: <1–5 тем через запятую>
   частота: <раз в день | утром+вечером | только будни>
   источники: <имена сайтов/RSS — опционально>
   ```

3. Бот фиксирует настройку и отвечает квитанцией в личке.
4. По расписанию бот присылает дайджест в личку: ≤4000 симв., 2–5 новостей,
   источники и ссылки, markdown MAX, без дублей и спама.
5. Управление: перенастройка — новое сообщение «темы: …»; стоп — «стоп»
   в личке либо удаление диалога (`bot_stopped` / `dialog_removed`
   — реестр чистится сам).

Канальная ветка (`target: channel`) ОТЛОЖЕНА, не отменена: связка
`bot_added` → `GET /messages?chat_id=` задокументирована, добирается
поверх ядра, если бета покажет спрос на «дайджест в свой канал».

## Гигиена кода (обязательно, пока токен общий с прод-каналами)

- Код эксперимента НЕ вызывает: канальные методы, `PUT /messages`,
  `DELETE /messages`, `PATCH /chats`, upload-методы. Разрешено:
  `GET /updates`, `GET /me`, `POST /messages` (только в диалоговые
  `chat_id` из реестра), `GET /messages?message_id=` (внутренние проверки).
- Тумблер-стоп: файл `local/pnews_PAUSED` — при его наличии планировщик
  не выполняет никаких отправок (poll реестра продолжает работать).
- Личка бота закреплена за экспериментом: публикации основной методики в неё
  запрещены (архив — `docs/bot-publications-archive.md`).
- Кап реестра в фазе 2: ровно 10 активных участников.
- Каждый отправленный дайджест и каждое событие — строка в
  `local/pnews_log.csv` (аудит без раскрытия содержимого).

## Техническая база (проверено по dev.max.ru, 06.11.2026)

- Домен API `https://platform-api2.max.ru`, токен в заголовке `Authorization`.
- `chat_id` диалога приходит боту в события `bot_started`
  (`GET /updates` / webhook) — use-case «Получение ID чата или канала».
- События лички: `bot_started`, `message_created`, `message_edited`,
  `dialog_cleared`, `dialog_muted`, `dialog_removed`, `bot_stopped`
  (объект `Update`).
- Отправка: `POST /messages?chat_id={dialog_chat_id}`, `format: markdown`,
  `notify: true`; лимиты: ≤4000 симв., ≤2 сообщ/сек на чат.
- Long polling (`GET /updates`) — «не для production» (лимит скорости
  и срок хранения событий); для эксперимента допустим при регулярном
  опросе (каждые 5–10 минут), production — webhook.
- Отложенной отправки в API нет — планировщик обязателен.
- TLS-транспорт с этой машины: `py` (3.14) + `MAX_HTTP=python` +
  `MAX_CA_CERT=local/russian_ca_bundle.pem` (см. `AGENTS.md`, раздел 5);
  системный `curl.exe` — для простых GET-проверок. Транспорт проверен
  рукопожатием 06.11 (HTTP 401 от `/me` без токена).

## Владелец событийного потока (важно)

Проверено по основному репо: ни один инструмент `E:\github\MAX` не читает
`GET /updates` — методика только отправляет/правит сообщения. Значит маркер
long polling `@se14808890_bot` свободен и с этого дня принадлежит
эксперименту. Правило: если в основной методике появится потребность
в событиях — сначала развести потоки (не делить один маркер между
программами).
