# Методика для ИИ-агента

Этот файл — операционная инструкция для любого ИИ-агента (локального консольного,
браузерного и т.п.), который работает с репозиторием. Прочитайте его целиком
перед первым заданием. Короткий вход для нового агента (что читать, что
проверить, чего не делать) — `docs/agent-onboarding.md`.

## 1. Назначение проекта

Репозиторий — рабочее место для управления несколькими каналами мессенджера MAX:
подготовка постов, публикация через Bot API, архив опубликованных постов и
описание стиля каждого канала.

## 3. Жизненный цикл поста (строго!)

Два цикла: **новые посты** — с утверждением, **правки опубликованных** — на
автопилоте. Согласование и отчёты — только в рабочем чате с агентом. Личка
бота AI Now с 07.11.2026 закреплена за новостным ботом; публикация в неё
запрещена (см. `docs/bot-publications-archive.md`).

### 3.1 Новые посты (утверждение — в рабочем чате с агентом)

> **Плотность публикаций не ограничена.** Ни в сутки, ни в неделю, ни
> интервалом между постами: сколько и когда выходит — определяет только
> контент-план владельца. Публикация — ежедневно в 07:15 (Планировщик),
> сбор статистики — в 07:00. Правило введено 2026-10-30, пересмотрено
> 2026-11-08 и упрощено 2026-11-10 (лимиты сняты).


```
draft ──(чек-лист 5а)──> показан человеку в рабочем чате ──(«ок» здесь)──> approved ──> published
```

1. **`draft`.** Агент создаёт файл поста в `roles/blogger/channels/<slug>/posts/`. Имя файла:
   `YYYY-MM-DD-kratkiy-slug.md` (дата — планируемая дата публикации).
2. **Чек-лист 5а** — прогнать до показа человеку, а не после.
3. **Показ черновика человеку** — текст поста целиком в рабочем чате с
   агентом (там, где человек отвечает сразу). Отправка черновика в личку
   бота запрещена: диалог закреплён за новостным ботом.
4. **Решение человека — в рабочем чате:** «ок» → публикация; правки → вносим
   в файл, показываем заново.
5. **`approved` → `published`.** После «ок» агент публикует (раздел 5),
   делает GET-проверку, обновляет архив, коммитит и отчитывается в рабочем
   чате ссылкой на пост.

### 3.2 Правки опубликованных постов (автопилот, без ожидания)

Правки по вычитке (опечатки, пунктуация, разметка) агент выполняет сразу по
циклу раздела 9: `GET` → сборка Markdown → `PUT` → GET-проверка → архив →
отчёт в рабочем чате со ссылкой → коммит. Утверждения не ждём — человек видит
результат в канале и просит откат/доправку при необходимости.

Запрещено: публиковать новый пост без показа черновика человеку; отправлять
посты со статусом `draft` в канал; генерировать изображения для постов без
прямого и явного указания человека (картинки предоставляет владелец).

## 4. Как писать новый пост

1. Откройте `roles/blogger/config/channels.json`, найдите канал (или попросите человека
   добавить новый, отредактировав реестр).
2. Прочитайте `roles/blogger/channels/<slug>/style.md`.
3. Прочитайте **3–5 последних опубликованных** постов из `roles/blogger/channels/<slug>/posts/`
   (файлы со `status: published`) — удерживайте стиль и не повторяйте темы.
4. Прочитайте `roles/blogger/channels/<slug>/style.md` целиком. Если в нём есть раздел
   **«Формат поста (ОБЯЗАТЕЛЬНЫЕ правила)»** — выполняйте эти правила
   буквально, пост с их нарушением публиковать нельзя (обязательные правила
   формата действуют в обоих каналах: `ainow` и `al` — изображение, жирный
   заголовок, отступы между блоками, цитата-призыв со ссылкой).
5. Создайте файл поста по формату из `README.md` со `status: draft`.
6. Покажите черновик человеку. При правках — исправляйте файл, а не ждите.

## 5. Как публиковать

### Вариант А: есть терминал с PHP (хостинг, машина с PHP)

```bash
php roles/blogger/bin/post.php roles/blogger/channels/<slug>/posts/<файл>.md
# предварительный просмотр:
php roles/blogger/bin/post.php roles/blogger/channels/<slug>/posts/<файл>.md --dry-run
```

Скрипт сам найдёт токен и `chat_id` по `channel` из front matter
(в `local/tokens.json`) и после успешной отправки обновит front matter.

### Вариант Б: агент умеет HTTPS-запросы сам (нет PHP рядом)

1. Прочитайте токен и `chat_id` канала из `local/tokens.json`.
2. Отправьте запрос:

```
POST https://platform-api2.max.ru/messages?chat_id={chat_id}
Authorization: {token}
Content-Type: application/json

{
  "text": "<текст поста (до 4000 символов)>",
  "format": "markdown",
  "notify": true
}
```

3. При успехе (HTTP 200): возьмите из ответа `message.body.mid` → `message_id`,
   `message.url` → `url`, `message.recipient.chat_id` → `channel_id`,
   `message.timestamp` (мс) → `published_at` (переведите в ISO 8601).
4. Обновите front matter файла поста: `status: published` + эти поля.
   Тело поста не меняйте.

### TLS и транспорт — источник сбоев №1 (актуально 06.11.2026, проверено)

У API MAX два HTTPS-хоста с разными цепочками сертификатов:

- `platform-api2.max.ru` — российская цепочка (корень Минцифры);
- `iu.oneme.ru` (CDN загрузок, раздел 8а) — до 03.11.2026 отдавал глобальную
  цепочку, с 06.11.2026 — тоже российскую (загрузки перестали проходить
  через обычный curl).

Ловушки, обе проверены на практике:

1. **curl.exe на Windows (schannel) ненадёжен для загрузки файлов.** Бэкенд
   schannel отклоняет российскую цепочку `iu.oneme.ru` даже с `--cacert`
   (`SEC_E_UNTRUSTED_ROOT` / `CERT_TRUST_IS_UNTRUSTED_ROOT`; проверено на
   curl 8.13.0 системном и 8.18.0 Git-овом — оба schannel, `--cacert` у
   schannel не заменяет системное доверие). С `--cacert` проходит
   `platform-api2`, но не CDN.
2. **Python с дефолтным контекстом** проходит `iu.oneme.ru` (берёт системные
   хранилища), но падает на `platform-api2.max.ru` с `unable to get local
   issuer certificate`, если русского корня нет в хранилище. Лечится
   совместным доверием: системное хранилище + cafile-бандл.

Рабочая схема (по умолчанию с 06.11.2026):

```powershell
# однократно: собрать бандл (корень + промежуточный с gu-st.ru)
curl.exe -s -o local/russian_trusted_root_ca.pem https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt
curl.exe -s -o local/russian_trusted_sub_ca.pem https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt
py -c "from pathlib import Path; r=Path('local/russian_trusted_root_ca.pem').read_text(); s=Path('local/russian_trusted_sub_ca.pem').read_text(); Path('local/russian_ca_bundle.pem').write_text(r.rstrip()+'\n\n'+s.rstrip()+'\n')"

$env:MAX_HTTP='python'
$env:MAX_CA_CERT=(Resolve-Path local/russian_ca_bundle.pem).Path
py roles/blogger/tools/publish_post.py --channel <slug> roles/blogger/channels/<slug>/posts/<файл>.md
```

- `MAX_HTTP=python` — транспорт urllib в `roles/blogger/tools/publish_post.py`: и JSON-запросы,
  и multipart-загрузка обложки делаются на stdlib; доверие = системное
  хранилище + `MAX_CA_CERT`.
- Вне скрипта тот же рецепт: `ssl.create_default_context(cafile=<бандл>)`
  и заголовок `User-Agent: curl/8.13.0` (с ним API отвечает охотнее).
- `MAX_CA_CERT` без `MAX_HTTP` работает только через curl — добавляется
  `--cacert` (проходит `platform-api2`, но не CDN, см. п. 1).
- `MAX_INSECURE=1` — крайняя мера отладки, в работе не использовать.
- Диагностика за минуту: `py -c` запрос к хосту — если HTTP-код пришёл
  (даже 404), TLS в порядке, проблема в другом; если ошибка сертификата/000 —
  TLS, переходите на py-транспорт.

Если PHP установлен, но API-запрос идёт с машины без сертификатов (ошибка TLS) —
см. переменные `MAX_CA_CERT` / `MAX_INSECURE` в `README.md`, либо выполнить
публикацию `roles/blogger/tools/publish_post.py` с `MAX_HTTP=python`.

Ещё нюансы рабочей машины (Windows): консоль PowerShell работает в cp1251 —
эмодзи и кириллицу из Python в консоль не вывести (`UnicodeEncodeError`).
Пишите результаты в файл и читайте его инструментом чтения файлов; срезы строк
для отладки выводите через `ascii(...)`. Python — запуск через **`py`**
(3.14; команда `python` перехватывается заглушкой Microsoft Store и падает) и
`curl.exe`; локального PHP нет — API-запросы через `py`-транспорт или `curl.exe`.

## 5а. Чек-лист перед публикацией (обязателен для каждого поста)

Перед `POST /messages` (и перед показом черновика человеку) прогнать
механические проверки — пост, опубликованный с нарушением формата, потом
приходится править в канале, а это лишний цикл согласования:

1. **Правила формата канала.** Открыть `roles/blogger/channels/<slug>/style.md`, раздел
   «Формат поста (ОБЯЗАТЕЛЬНЫЕ правила)», и проверить пост по каждому пункту
   буквально (сейчас такие разделы есть у обоих каналов — `ainow` и `al`).
2. **Изображение** (если правило требует): картинку присылает владелец.
   Проверить, что файл существует, загружен через upload-API (раздел 8а),
   токен включён в `attachments`. Если картинки нет — **не генерировать её
   самостоятельно**, а запросить у владельца и придержать публикацию.
   Если в посте есть видео — картинка не нужна: видео заменяет обложку
   (`roles/blogger/channels/ainow/style.md`, раздел 1а).
3. **Длина:** финальный текст (с разметкой) ≤ 4000 символов — посчитать
   скриптом, не на глаз.
4. **Финальная цитата-призыв:** последний блок — цитата `> **Подписывайтесь
   на <канал>** — [текст](URL)`; ссылка ведёт на канал и отвечает `200`
   (`curl.exe -s -o NUL -w "%{http_code}" -I URL`).
5. **Заголовок** — жирным, одна строка, без точки в конце.
6. **Воздух:** блоки разделены `\n\n`, один блок — одна мысль.
7. **Перелинковка:** 1–2 ссылки на прошлые посты канала AI вплетены в
   текст поста, в подходящий абзац. Отдельного блока ссылок в конце
   поста нет (правило 7 в `roles/blogger/channels/ainow/style.md`).

После публикации: `GET /messages/{mid}` — вложение на месте, текст совпадает,
инлайн-разметка цела (цитату GET не показывает — см. раздел 9).

## 6. После публикации — git

> **Перед публикацией — `git pull --rebase origin main`.** По расписанию и по
> ручным прогонам над репозиторием работает несколько запусков. Пост на сегодня
> мог уже выйти и быть закоммичен: если файл в `status: published`, повторно
> публиковать нельзя. Порядок: `pull` → сверить дату, статус и `message_id` →
> и только потом `publish_post.py` / `publish_telegram.py`. Ошибка 2026-11-03:
> два запуска опубликовали один и тот же пост 03.11, дубль удалён через
> `DELETE /messages?message_id=...` (200, затем GET 404).

Каждая публикация — отдельный коммит, чтобы история репозитория совпадала с
историей канала:

```
roles/blogger/channels/<slug>: опубликован пост <файл>
```

Коммиты делает агент (или человек) после успешной отправки. Пуш в GitHub — по
обычному workflow команды (например, в конце рабочей сессии).

## 7. Токены и доступ

- Токены только в `local/tokens.json` (gitignored). Не упоминайте токены в
  постах, коммитах, README и логах.
- Структура `local/tokens.json`: ключ — `slug` канала (обязательно совпадает с
  папкой и полем `channel` поста), значения — `token` (access token бота),
  `chat_id` (ID канала), опционально `bot_username`.
- **Один бот может вести несколько каналов**: один и тот же `token` в записях
  разных каналов, у каждого канала свой `chat_id`. Скрипт выбирает нужный по
  полю `channel` поста. Пошаговая настройка бота — `docs/bot-setup.md`.

## 8. Технические ограничения API MAX

- Домен `https://platform-api2.max.ru`, токен в заголовке `Authorization`
  (не в query-параметрах).
- Не более **2 сообщений/сек** в один канал; текст до **4000 символов**.
- **Редактирование — тот же лимит: не более 2 сообщений/сек в один канал.**
  При массовой проверке и правке старых постов ставьте паузу между запросами
  (например, 0,5–1 сек на пост) или обрабатывайте канал очередью.
- Каналы: отправка только с `notify = true` (или без поля).
- Отложенной публикации в API нет. Не строим её на уровне постов, пока в
  репозитории не появится планировщик.
- Стратегия отладки: сначала `--dry-run`, затем отправка.

3. Прикрепление: в `POST /messages` или `PUT /messages?message_id=...` передать

   обычно (Markdown), существующие вложения без поля `attachments` сохраняются.
4. Ссылку на картинку на CDN берём из `GET /messages/{mid}` →

   `image:` front matter поста.
5. Проверка: `GET /messages/{mid}` — `attachments == 1`, текст и разметка не
   изменились.

**Изображения не генерируются.** Картинку для поста присылает владелец —
это правило по умолчанию. Генерация (Pillow, `roles/blogger/tools/make_card.py` и любые
другие способы) допускается только по прямому и явному указанию владельца
в текущей задаче. Если картинки нет — запросить её и придержать публикацию;
подставлять заглушку или генерировать «по своему усмотрению» нельзя.

Техническая справка по генератору (использовать только при таком указании):
Pillow, тёмный градиент + неоновые элементы, шрифты

только через paste с растушёванной маской: blend всего холста затемняет уже
нарисованный текст. Пример: `local/make_card_1029.py`.

## 9. Правка опубликованного поста

Правка делается в том же сообщении канала (`PUT /messages?message_id=...`) —
дата публикации, ссылка и просмотры сохраняются. Бот-админ может править посты
любой давности.

```
PUT https://platform-api2.max.ru/messages?message_id={message_id}
Authorization: {token}
Content-Type: application/json

{ "text": "<новый текст>", "format": "markdown" }
```

- Вложение (картинку) не передавайте — оно сохранится. `attachments: null`
  тоже оставляет вложения без изменений.
- Ответ при успехе: `{"success": true}`. Проверяйте результат
  `GET /messages/{message_id}`.
- Согласование: правки опубликованных постов применяются сразу, на автопилоте
  (раздел 3.2); в рабочем чате — отчёт о результате со ссылкой. Новые посты —
  утверждение в рабочем чате (раздел 3.1).
- После правки: обновите файл поста в архиве (тело — итоговый Markdown,
  добавьте `edited_at: <дата-время правки в ISO 8601, МСК>`), коммит.

### Разметка и UTF-16 (важно!)

- В ответах API (`GET /messages`, `body.markup`) позиции `from`/`length`
  считаются в **UTF-16 кодовых единицах**: эмодзи вне базовой многоязычной
  плоскости (🔥, 💡, 📂, 🚀 и т.п.) занимают **2 единицы**, а не одну кодовую
  точку. Python/JS считают кодовые точки — при реконструкции Markdown позиции
  нужно пересчитывать (префикс-суммы: `2 if ord(ch) > 0xFFFF else 1`).
- В старых постах встречаются **неразрывные пробелы** (`\xa0`) и **неразрывные
  дефисы** (`‑`, U+2011): «ИИ‑инструменты», «Подписывайтесь на\xa0AI». При
  поиске подстрок и точных заменах сначала проверяйте реальные символы
  (в Python — `ascii(...)`, иначе опечатка выглядит как совпадение).
- Синтаксис Markdown, который понимает MAX (по документации и практике):
  `**жирный**`, `*курсив*` / `_курсив_`, `[текст](url)`, `~~зачёркнутый~~`,
  `++подчёркнутый++`, `^^выделение^^`, `# заголовок`, `` `code` ``.
- Цитата `> текст`: при отправке **работает** — `>` исчезает из текста, блок
  рендерится цитатой. Но `GET /messages/{mid}` **не возвращает** blockquote
  в массиве `markup` (там только инлайн-разметка: strong, link и т.п.).
  Отсутствие цитаты в markup — не признак ошибки. Признак того, что цитата
  распарсилась: в `text` нет ведущего `>`, а инлайн-разметка внутри блока
  (жирный, ссылка) сохранилась. Финальная проверка — визуально в клиенте.
- Надёжный способ правки: собрать Markdown вручную по фрагментам разметки
  (срезы текста по пересчитанным позициям), а не генерировать вслепую —
  в старых постах разметка на сервере может быть частично сдвинута (следы
  ручных правок при публикации). После `PUT` сервер заново парсит Markdown —
  артефакты разметки исчезают (проверено на посте от 22.07).

### Практический цикл правки (проверено на постах 22.07 и 28.09)

1. `GET /messages/{message_id}` — снять текст и разметку поста (позиции —
   UTF-16, см. выше). Сохранить JSON в `local/` для отладки.
2. Внести текстовые правки в файл поста в архиве.
3. Собрать Markdown точными заменами по фрагментам разметки, каждая замена —
   с проверкой числа вхождений (ожидалось/найдено). Рабочие примеры —
   `roles/blogger/tools/build_markdown.py` (сборка md из текста и разметки),
   `roles/blogger/tools/markup_fragments.py` (снятие фрагментов) и
   `roles/blogger/tools/ensure_cta_quote.py` (пакетные правки + проверка после PUT).
4. `PUT /messages?message_id=...` с `{"text": ..., "format": "markdown"}`,
   без вложений.
5. `GET /messages/{message_id}` — проверить: правки на месте, вложение
   сохранилось, фрагменты разметки корректны (с учётом UTF-16).
6. Обновить файл поста: тело — итоговый Markdown (у импортированных постов
   тело — простой текст, после первой правки заменяется Markdown-версией),
   добавить `edited_at` (дата-время правки, ISO 8601, МСК).
7. Отчитаться в рабочем чате (ссылка на пост + список исправлений) —
   ожидания ответа нет. Коммит и пуш.

Правки применяются сразу (автопилот, раздел 3.2). Правка поста и отправка
нового — обычные сообщения, у них общий лимит 2 сообщения/сек.

### Проверка CTA при любой правке (введено 2026-10-29)

При каждой правке старого поста проверять нижний блок: последний абзац —
цитата с призывом и ссылкой на канал (`> **Подписывайтесь на
[AI](https://max.ru/channel_ainow)** — …`). Если строки призыва нет или она
не цитата — привести к формату правила 4 из `style.md`. Текст призыва каждый
раз новый (фразы не повторяются между постами; машинный реестр фраз —
`roles/blogger/channels/<канал>/cta-phrases.json`, человекочитаемая таблица —
`proofread.md`, раздел «CTA»). Проверка выполняется и для «чистых» постов —
сам по себе она повод для правки.
