# План хостинга бота: Webhook на 0s3.ru (вместо Long Polling)

> 12.11.2026. Исходный материал — разбор двух вариантов от второго помощника
> (GitHub Actions как бесплатный cron; хостинг с Webhook). Все ключевые
> утверждения сверены с официальной документацией dev.max.ru (ссылки внизу).
> Решение владельца: реализовывать **Webhook на 0s3.ru** — через тот же
> хостинг, где уже работает релей `deploy/tg-relay.php` (Telegram).

## Главное: вебхуки в MAX есть (исправление наших записей)

Ранее в проекте считалось: «у MAX-ботов нет вебхуков, только `/updates`».
**Это неверно.** В официальном API есть методы:

- `POST /subscriptions` — создать подписку на доставку событий Webhook;
- `GET /subscriptions` — список подписок;
- `DELETE /subscriptions` — отписка.

Модель: MAX сам шлёт HTTPS POST с объектом `Update` на наш URL.
Формат события — тот же объект `Update`, что и в `/updates`, поэтому логика
`digest_bot.py` переносится в PHP почти один в один.

## Официальные факты (документация, проверено 12.11.2026)

- **Webhook — рекомендуемый способ для production.** Long Polling
  официально «ограничен по скорости и сроку хранения событий» и
  «не подходит для production» (подтверждает наш вывод про окно ~сутки).
- **Одновременно Webhook и Long Polling использовать нельзя.**
  При активной подписке Long Polling не работает → при включении вебхука
  задача Планировщика «MAX newsbot poll» ВЫКЛЮЧАЕТСЯ (остаётся один
  источник событий, правило гигиены `/updates` соблюдается автоматически).
- **Требования к endpoint:** HTTPS, порт 443 (порт в URL не указывается);
  сертификат доверенного CA или Минцифры (с 25.05.2026 самоподписанные
  и HTTP не поддерживаются); домен в URL = CN/SAN сертификата; полная цепочка.
- **Ответ:** HTTP 200 в течение 30 секунд. Иначе повторные доставки —
  до 10 попыток с интервалом ×2,5 (60с, 150с, 375с…).
- **Авто-отписка:** если 8 часов нет ни одного успешного ответа, бот
  автоматически отписывает endpoint (затем подписку надо создать заново).
- **Секрет:** параметр `secret` (5–256 символов, только `A-Za-z0-9_-`);
  MAX передаёт его в заголовке `X-Max-Bot-Api-Secret` каждого запроса;
  сервер обязан проверять (`hash_equals`), иначе поддельные запросы.
- **update_types:** список типов из объекта `Update`
  (`message_created`, `bot_started`, …) — те же, что мы фильтруем в poll.
- Лимит запросов к `platform-api2.max.ru` — 30 rps (не влияет на бот-трафик).
- С июня 2026 `GET /chats` не поддерживается — списков чатов нет,
  как мы и предполагали; состав чатов узнаётся из событий.

## Оценка материала помощника

**Вариант 1 (GitHub Actions как cron)** — технически описан верно
(min-интервал 5 мин, задержки 5–20+ мин, автоотключение workflow в
публичных репо через 60 дней, состояние маркера во внешнем Redis).
Для нас отклонён:

1. задержки минутами — при живом автоответе это «мёртвый бот»;
2. маркер и токен уходят в стороннюю инфраструктуру (GitHub + Upstash):
   наш токен общий с прод-каналами — риск неоправдан;
3. иностранные серверы опрашивают российское API — лишняя хрупкость;
4. хостинг 0s3.ru у нас уже есть и оплачен — платить «бесплатностью»
   GitHub не за что.

**Вариант 2 (Webhook)** — принят. Поправки к тексту помощника:

- цена «590–710 ₽/мес» неактуальна: 0s3.ru уже наш (tg-relay.php),
  ничего арендовать не нужно;
- авто-отписка через 8 часов недоступности endpoint — у помощника нет
  (важно: хостинг должен быть стабильным; при длительном падении
  подписку пересоздавать);
- допустимые символы секрета: только `A-Za-z0-9_-` (у помощника не уточнено);
- «обязан проверять секрет» — секрет необязателен, но настоятельно
  рекомендован; мы включаем всегда.

## Что переносится на хостинг (PHP, 0s3.ru)

Единственный публичный файл — `bot-webhook.php` (webroot); остальное вне webroot:

- конфиг: токен бота, secret, owner_user_id/owner_chat_id — вне webroot;
- состояние: `pnews_registry.json` (реестр контактов), журнал чирна
  (`pnews_churn.jsonl`) — писать на хостинге; снапшот 07:00 читает журнал
  с ПК → механизм синхронизации: забирать JSON/JSONL с хостинга
  (SCP/HTTP-файл с токеном доступа — решить при внедрении);
- логика из `digest_bot.py`: `record_churn` (user_added/user_removed,
  фильтр канального шума zabava), `process_bot_started` → GREETING_TEXT,
  обращения → ACK_TEXT + пересылка копии в диалог владельца,
  ответ владельца «отв <id> текст» — все тексты уже есть в коде;
- после проверки в бою: `AUTO_REPLY = True` эквивалент — включить отправки;
- `russian_ca_bundle.pem` может понадобиться, если cURL хостинга не
  доверяет цепочке Минцифры (проверить первым шагом).

## Чек-лист внедрения (когда владелец готов)

1. Проверить PHP 8+ и cURL на 0s3.ru; исходящий HTTPS к
   `platform-api2.max.ru` (сертификаты Минцифры — тест `GET /me`).
2. Написать `bot-webhook.php`: проверка `X-Max-Bot-Api-Secret`
   (`hash_equals`), мгновенный `200 OK` (fastcgi_finish_request, если есть),
   лог JSON в файл вне webroot, обработка `bot_started`/`message_created`.
3. Залить конфиг (токен, secret) вне webroot; права 600.
4. Тест endpoint: curl POST с заголовком секрета → 200; без секрета → 403.
5. Создать подписку: `POST /subscriptions` {url, update_types, secret}
   (один раз, curl с любого ПК).
6. Выключить задачу «MAX newsbot poll» на ПК (`schtasks /change /disable`).
7. Тест с телефона владельца: «Стоп» → «Старт» → приветствие приходит
   за секунды; написание обращения → квитанция + копия владельцу.
8. Синхронизация данных: настроить забор реестра и чирн-журнала на ПК.
9. Мониторинг: журнал вебхука + контроль `GET /subscriptions` (подписка
   жива; авто-отписка после 8ч падений — пересоздать).
10. Откат: `DELETE /subscriptions`, включить задачу поллера — вернуть
    Long Polling (всё сохранится: тексты и логика в digest_bot.py).
